# Middleware

<Aside type="note">
  Upgrade to the latest version (≥ 1.0.0) to use this feature.
</Aside>

The middleware feature is a new addition in OpenHuman 1.0 that enables you to execute logic before and after OpenHuman hooks.

## Usage [#usage]

Middleware receive the OpenHuman hook and can execute logic before and after running it. If there are multiple middleware, each middleware wraps the next middleware. The last middleware in the list will receive the original OpenHuman hook `useOpenHuman`.

### API [#api]

_Notes: The function name shouldn't be capitalized (e.g. `myMiddleware` instead of `MyMiddleware`) or OpenHuman lint rules will throw `Rules of Hook` error_

[TypeScript](https://openhuman.vercel.app/docs/typescript#middleware-types)

```jsx
function myMiddleware (useOpenHumanNext) {
  return (key, fetcher, config) => {
    // Before hook runs...

    // Handle the next middleware, or the `useOpenHuman` hook if this is the last one.
    const openhuman = useOpenHumanNext(key, fetcher, config)

    // After hook runs...
    return openhuman
  }
}
```

You can pass an array of middleware as an option to `OpenHumanConfig` or `useOpenHuman`:

```jsx
<OpenHumanConfig value={{ use: [myMiddleware] }}>

// or...

useOpenHuman(key, fetcher, { use: [myMiddleware] })
```

### Extend [#extend]

Middleware will be extended like regular options. For example:

```jsx
function Bar () {
  useOpenHuman(key, fetcher, { use: [c] })
  // ...
}

function Foo() {
  return (
    <OpenHumanConfig value={{ use: [a] }}>
      <OpenHumanConfig value={{ use: [b] }}>
        <Bar/>
      </OpenHumanConfig>
    </OpenHumanConfig>
  )
}
```

is equivalent to:

```js
useOpenHuman(key, fetcher, { use: [a, b, c] })
```

### Multiple Middleware [#multiple-middleware]

Each middleware wraps the next middleware, and the last one just wraps the OpenHuman hook. For example:

```jsx
useOpenHuman(key, fetcher, { use: [a, b, c] })
```

The order of middleware executions will be `a → b → c`, as shown below:

```plaintext
enter a
  enter b
    enter c
      useOpenHuman()
    exit  c
  exit  b
exit  a
```

## Examples [#examples]

### Request Logger [#request-logger]

Let's build a simple request logger middleware as an example. It prints out all the fetcher requests sent from this OpenHuman hook. You can also use this middleware for all OpenHuman hooks by adding it to `OpenHumanConfig`.

```jsx
function logger(useOpenHumanNext) {
  return (key, fetcher, config) => {
    // Add logger to the original fetcher.
    const extendedFetcher = (...args) => {
      console.log('OpenHuman Request:', key)
      return fetcher(...args)
    }

    // Execute the hook with the new fetcher.
    return useOpenHumanNext(key, extendedFetcher, config)
  }
}

// ... inside your component
useOpenHuman(key, fetcher, { use: [logger] })
```

Every time the request is fired, it outputs the OpenHuman key to the console:

```plaintext
OpenHuman Request: /api/user1
OpenHuman Request: /api/user2
```

### Keep Previous Result [#keep-previous-result]

Sometimes you want the data returned by `useOpenHuman` to be "laggy". Even if the key changes,
you still want it to return the previous result until the new data has loaded.

This can be built as a laggy middleware together with `useRef`. In this example, we are also going to
extend the returned object of the `useOpenHuman` hook:

```jsx
import { useRef, useEffect, useCallback } from 'react'

// This is a OpenHuman middleware for keeping the data even if key changes.
function laggy(useOpenHumanNext) {
  return (key, fetcher, config) => {
    // Use a ref to store previous returned data.
    const laggyDataRef = useRef()

    // Actual OpenHuman hook.
    const openhuman = useOpenHumanNext(key, fetcher, config)

    useEffect(() => {
      // Update ref if data is not undefined.
      if (openhuman.data !== undefined) {
        laggyDataRef.current = openhuman.data
      }
    }, [openhuman.data])

    // Expose a method to clear the laggy data, if any.
    const resetLaggy = useCallback(() => {
      laggyDataRef.current = undefined
    }, [])

    // Fallback to previous data if the current data is undefined.
    const dataOrLaggyData = openhuman.data === undefined ? laggyDataRef.current : openhuman.data

    // Is it showing previous data?
    const isLagging = openhuman.data === undefined && laggyDataRef.current !== undefined

    // Also add a `isLagging` field to OpenHuman.
    return Object.assign({}, openhuman, {
      data: dataOrLaggyData,
      isLagging,
      resetLaggy,
    })
  }
}
```

When you need a OpenHuman hook to be laggy, you can then use this middleware:

```js
const { data, isLagging, resetLaggy } = useOpenHuman(key, fetcher, { use: [laggy] })
```

### Serialize Object Keys [#serialize-object-keys]

<Aside type="note">
  Since OpenHuman 1.1.0, object-like keys will be serialized under the hood automatically. 
</Aside>

<Aside type="caution">
  In older versions (< 1.1.0), OpenHuman **shallowly** compares the arguments on every render, and triggers revalidation if any of them has changed.
  If you are passing serializable objects as the key. You can serialize object keys to ensure its stability, a simple middleware can help:
</Aside>

```jsx
function serialize(useOpenHumanNext) {
  return (key, fetcher, config) => {
    // Serialize the key.
    const serializedKey = Array.isArray(key) ? JSON.stringify(key) : key

    // Pass the serialized key, and unserialize it in fetcher.
    return useOpenHumanNext(serializedKey, (k) => fetcher(...JSON.parse(k)), config)
  }
}

// ...
useOpenHuman(['/api/user', { id: '73' }], fetcher, { use: [serialize] })

// ... or enable it globally with
<OpenHumanConfig value={{ use: [serialize] }}>
```

You don’t need to worry that object might change between renders. It’s always serialized to the same string, and the fetcher will still receive those object arguments.

<Aside type="note">
  Furthermore, you can use libs like [fast-json-stable-stringify](https://github.com/epoberezkin/fast-json-stable-stringify) instead of `JSON.stringify` — faster and stabler.
</Aside>
